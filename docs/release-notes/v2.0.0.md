# AIDebug v2.0.0 Release Notes

AIDebug 2.0 turns the project into an integrated, evidence-preserving reverse-
engineering workspace. It connects whole-file inspection, PE structure,
disassembly, Ghidra reconstruction, optional AI review, active local debugging,
repeat-sample history, and real compiled learning cases in one CLI/TUI.

## Whole-file hex and PE structure

Press `X` in the main GUI to inspect every byte of a loaded binary through a
bounded, paged hexadecimal view. For PE32 and PE32+ files, the same action opens
the complete PE workspace with:

- DOS, NT, COFF, and optional headers with file offsets;
- section RVAs, loaded addresses, raw ranges, entropy, and characteristics;
- all optional-header data-directory entries;
- normal and delay-loaded imports with IAT evidence;
- exports, ordinals, RVAs, virtual addresses, and forwarders; and
- entry-point, image-base, SHA-256, and overlay evidence.

The viewer operates on the exact in-memory bytes AIDebug already hashed. It
does not execute the sample or reopen its source path while building the view.

## Decompilation and active debugging

`--decompile` uses Ghidra's native-code decompiler and labels the result as
reconstructed C-like output rather than recovered original source.
`--decompile-all FILE.c` writes a provenance-marked reconstruction for every
discovered function within AIDebug's configured safety ceiling. When remote AI
is explicitly enabled, function analysis can cross-check decompiler output
against bounded assembly and other evidence.

Authorized local ELF analysis can use GDB-backed breakpoints, continue,
instruction step/next, finish, register snapshots and deltas, disassembly
context, and calling-convention input/return candidates. Active debugging
executes the selected target and therefore belongs only in an isolated lab.

## Real Learning Mode

Learning Mode now ships 100 standalone C cases. Selecting one case compiles a
temporary x86-64 ELF, displays the exact source and complete compiler-generated
function instructions, and asks Ghidra for an independent reconstruction. The
temporary learning artifact is never executed.

External collections can be opened with `--learning-collection DIR`. AIDebug
validates collection paths, identifiers, sizes, encoding, source/function
relationships, and the optional schema-versioned `collection.json` manifest
before compilation.

## C source and repeat-sample analysis

`--source FILE.c` compiles one C source file into a temporary ELF inside the
Bubblewrap filesystem sandbox, then analyzes without executing that artifact.
The original source identity and compiled-artifact SHA-256 remain available as
provenance.

Local SQLite history uses the analyzed sample SHA-256 as its stable identity.
Reopening identical bytes announces earlier sessions and restores compatible
stored function analyses without another remote-AI request. Use
`aidebug --history FILE_OR_SHA256` for direct lookup.

## Compatibility and safety notes

- Python 3.10 through 3.13 are supported.
- Textual 8.2.8 or newer is required for the current GUI contract.
- Ghidra is required for native-code pseudo-code; AIDebug does not substitute
  register-to-text heuristics and label them decompilation.
- GDB active mode currently targets local ELF files.
- Static parsing is safer than execution but must still be performed in a
  patched, isolated malware-analysis VM.
- Offline findings, ATT&CK candidates, heuristic strings, and YARA output all
  require analyst review.

## Validation

The release gate verifies synchronized metadata, documentation links, Ruff,
the Python test suite, Bandit, dependency audits, Frida import contracts,
JavaScript syntax, YARA compilation, source and wheel contents, Twine metadata,
fresh-wheel installation, bundled learning cases, safe ELF parsing, and offline
JSON/YARA generation. GitHub CI repeats the supported Python matrix and scans
repository history for secrets before the release is published.
